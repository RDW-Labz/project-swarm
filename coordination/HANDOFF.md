## Lesson from this session (worth reading before the next audit-style ticket)

Several "test" tickets this session (T-0405/T-0409/T-0413/T-0417/T-0422) are audits: review existing coverage against an epic's acceptance criteria, fix genuine gaps, and say so plainly if there are none. **T-0409's own audit concluded "no gap" and was wrong** — an Opus review (required because the ticket is marked sensitive) found two real vacuous assertions (a concurrent-isolation test that couldn't actually fail even with a shared grant key, and a legacy-mode test with dead code that never invoked the command it claimed to test). Lesson: run the Opus review before trusting an audit's "no gap" conclusion, even when the audit looks thorough — don't skip or shortcut review on audit-type tickets just because they "didn't change anything."

Also caught directly (not via Opus) during T-0423 review: a CLI wrapper synthesized `{sensitive: false}` whenever `--ticket` was omitted, silently defeating the fail-closed null-ticket protection that a prior review round had specifically fixed one layer down. Worth remembering: a fail-closed fix at one layer can be quietly undone by a caller one layer up.

A `runCpuRunnerJob` elapsed-time test flaked only under the full ~6500-test suite's heavy parallel load (never in isolation) — hardened to a wider sleep gap + ratio-based assertion instead of a tight absolute-ms margin. If a timing-sensitive test flakes only under full-suite load again, don't chase it by rerunning: widen the margin or switch to a relative check, same as this one.
