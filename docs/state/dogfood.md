## Phase 14 notes

- **How it was done:** measure first. A stress harness (`bench/throughput/stress.mjs`) showed 500 jobs in 16 s but 1000 in 301 s; CPU profiles and then stage timings pointed at the real causes, one at a time. The first guesses (thread pool size, in-memory context for API jobs) did nothing and were removed.
- **The big one** was not in the plan: every API job claimed a slot of the local host, whose capacity is for workers that run code, so a run was never more than about 4 requests deep however high the lane limit was. It was found by timestamping when requests start (batches of exactly four).
- **Rule exception:** no worker jobs for this phase (see the scoreboard row); the swarm ran the Claude review job only.
- **Review job:** Claude Opus, 2 high and 6 medium, all fixed (see CHANGELOG 1.71.0). One thing it could not see and I could not prove with a test: that 2,048 API jobs started at once cannot overshoot a spend cap. The reservation step that checks caps is a serial chain (`admissions`), one job at a time, so the check-then-reserve is atomic per job; the existing cap tests cover that path, not a 2,048-wide one.
- **Not built:** an append-only state log (measured not to be needed), copy-on-write workspaces (not a cost in the profile), batch mode (waits for your go-ahead), more hosts (waits for the dev2 link).
