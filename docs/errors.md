# Production errors become tickets

Phase 19, part C1 ([design](plans/phase19-design.md)). Only services already in use: the `vercel` CLI you are logged in with. No Sentry, no new key.

- `swarm errors pull` runs `vercel logs --query 'level:(error OR fatal) AND environment:production' --since 15m --limit 1000 --json --non-interactive` in the project folder (the linked Vercel project) and turns the error lines into events. `--dry-run` shows what it would take and stores nothing. The command can be replaced in the profile (`errors.source.argv`, no shell). Run it by hand or from a schedule: Vercel keeps runtime logs only a short time on the free plan, so pull more often than that.
- `swarm errors ingest FILE|-` takes JSON lines from anywhere else (`{at, message, route, stack}` or the vercel format). This is also how a later source (the app writing its own errors, planned with the starter kit) plugs in.
- **Scrubbing, before anything is stored** (text is cut to 4 KB first so hostile input cannot slow it down): emails, phone numbers, ids (UUIDs, long hex), IP addresses, tokens and keys (bearer, JWT, `sk_`-style), `password=`/`token=`/`cookie`-style pairs, query strings, home folders. Request paths lose record ids (`/orders/42` becomes `/orders/:id`). Stack frames keep the function and the file inside the app, with no line numbers and no `node_modules`. Also connection-string passwords, URL fragments, form bodies, Postgres `Key (col)=(value)`, card numbers, Stripe-style ids (`cus_`, `pi_`), long mixed ids, percent-encoded and fullwidth/zero-width disguises (text is normalised first). Text that still looks like a secret is withheld. **A person's name written as plain words inside a message is not recognised**, and look-alike letters from another alphabet can dodge a word list: the scrubber targets identifiers, so look at a proposal's notes before you approve it.
- **One group per error:** the fingerprint is the error type, the message with its ids and numbers taken out, and the top app frames (or the route when there is no stack). A repeat only raises the count.
- Limits per pull: at most 20 new proposals (the rest wait for the next pull), at most 5 inbox decisions plus one summary, events dated more than 30 days back or more than 5 minutes ahead are dropped, 2000 groups kept (a full store drops a fixed or ignored one first). One lock file keeps a cron pull and a hand command from overwriting each other; a damaged `errors.json` stops the command instead of being replaced.
- **A new group makes one `proposed` ticket** (`swarm tickets --status proposed`): title (just `ERR-xxxxxxxx`) and acceptance are fixed words (not even the route is in the title), the scrubbed text is only quoted data in `notes`, and no worker runs it until you name its files and approve it (`swarm tickets T-0042 --files a,b --yes`, then `--approve --yes`). Payments, checkout, billing and auth routes get risk high and the ticket is sensitive.
- **If a fixed error comes back** (its ticket is done and a newer event arrives) it becomes a new proposal linked to the old one. Events from before the fix, and for 30 minutes after it was noticed (the old deploy still running), do not reopen it. The same error on a payments or auth route is its own group even when its stack is shared with other routes.
- **Severity (profile `errors`):** `critical` route patterns (default: payments, checkout, billing, stripe, auth, login and signup, at any depth: `/payments`, `/en/checkout`, `/api/v1/payments/charge`; patterns are `*` within a folder name and `**` for any depth, case does not matter) and a `spike` (default 20 in 10 minutes) are an **inbox decision now** (`swarm inbox`; a spike again only after an hour). Everything else waits for `swarm errors digest`, which writes `.swarm/reports/errors-digest-DATE.md` once per new activity.
- `swarm errors list [--status open|ignored|fixed]`, `show ERR-xxxxxxxx`, `ignore ERR-xxxxxxxx --reason TEXT` (never ticketed or notified again), `resolve ERR-xxxxxxxx` (you fixed it by hand).
- Nothing here deploys, merges or sends anything. Phone notification is the next part of Phase 19.

Checked against the real CLI (1.118.0): entries are `{type:"log", data:{level, message, timestamp, requestPath, requestId, deploymentId, stream, ...}}` and the last line is `{type:"summary", recordsReturned, ...}`. Vercel calls what an app writes to stderr `warn`, so an Error-shaped message on stderr counts as an error (a plain warning does not); an app that logs JSON is read by the level inside its message. On the Pro plan a window like `--since 24h` is refused ("outside the available retention"); the default 15 minutes works, so pull at least that often.
